How lovearound works

Signals can be sent and received by more than the app. A lamp, a soft toy, a small screen or your own script will do. This is how it all works and how to connect to it.

Overview REST API WebSocket ESP32 toy

What a signal is

A signal is a heart someone sends to a person they’re thinking of. It carries nothing: no text, no sender’s name, not even the time it was pressed. All the recipient sees is that someone thought of them.

A signal only lives in the moment. It reaches the devices that are online right now. If the person is offline, the signal isn’t queued and won’t arrive later — by design.

Key terms

TermWhat it is
AccountGoogle sign-in in the Mac or Windows app. Created the first time you sign in.
Love IDYour 10-character code, for example GSSV7-A33HN, and the link with it: lovearound.me/i/GSSV7-A33HN. People add you to their list with it.
ContactA person in your list. It has an id and a label only you can see. The person isn’t told they were added.
DeviceA toy, lamp or script connected to your account with its own token. It can receive signals, send them, or both.
EventWhat the server delivers to online devices. There is one type for now: signal.
StreamThe WebSocket a device keeps open to receive events.

How a signal travels

  1. The sender makes a single HTTP request, POST /v1/events, with the id of a contact from their list.
  2. The server finds who is behind that contact and answers 202: the signal is accepted.
  3. Every device of the recipient that has a /v1/stream open right now gets the same event and lights up.

Signals are sent only over REST and received only over WebSocket. The stream is one-way: the server ignores anything a client writes to it. That way sending has one path and one place for every check.

What the server doesn’t do

  • It doesn’t say who a signal is from. No event has a from field, and none ever will. Not even the server log records the sender.
  • It doesn’t store signals. There is no history and no queue for people who are offline. That’s why 202 means “accepted”, not “delivered”.
  • It doesn’t reveal who is who. Clients only see the ids of contacts in their own list. People’s internal identifiers never leave the server.
  • It doesn’t confirm that a Love ID exists. A wrong code is added just like a right one; signals to it simply go nowhere. Guessing codes gets you nothing.
  • It doesn’t tell anyone they were added or removed.

Access and tokens

The server’s address:

https://api.lovearound.me

Every request, including opening the WebSocket, carries a token in the Authorization: Bearer … header. There are two kinds of token:

WhoTokenWhat it can do
AppA Firebase ID token after Google sign-inEverything: account, contact list, devices, signals
Devicedev_ followed by 32 letters and digits. Created in the app: Settings → DevicesRead the contact list, send signals (if allowed to send), receive them (if allowed to receive). Anything else is 403

Your own device or script only needs a device token. It is shown once. If it leaks, disconnect the device in the same place: the token and every connection opened with it stop working at once.

Compatibility

  • Every path starts with /v1. Breaking changes will only come under a new version.
  • Every event has a type and a version v. Skip any type or v you don’t know, and your device will survive new kinds of events.
  • Skip unknown fields in responses too: there may be more of them over time.
