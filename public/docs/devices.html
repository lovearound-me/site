Device protocol

For makers of boards and toys: tell the server what your device is made of, and the lovearound apps draw its settings for you.

Two ways in

A device says what it is made of: a ring of LEDs, a buzzer, a button. These are its parts. Each kind of part has standard settings, and every lovearound app draws a row for each part on the device’s card: color, brightness, effect, volume, whom the button sends to. You write no settings screen of your own.

The same messages travel two ways:

  • A Wi‑Fi device talks to the server itself, with its own device token: REST to send and report, the stream to receive. It can be set up over Bluetooth from the phone, by pairing by code, or with a token from Settings → Devices.
  • A Bluetooth-only toy talks to the owner’s phone, and the phone talks to the server for it. See Bluetooth-only toys.

Either way a device gets a signal and nothing else about it: no sender, no color of the sender, no text. There is no setting by sender, and there never will be: no “light differently for different people”.

about: what a device is made of

{
  "proto": 1,
  "model": "heart-ring",
  "firmware": "2.1.0",
  "wants": ["receive", "send"],
  "parts": [
    { "id": "ring", "kind": "light", "leds": 24,
      "settings": ["color", "brightness", "effect", "speed", "duration", "idle"],
      "effects": ["glow", "heartbeat", "wave", "sparkle", "rainbow"],
      "default": { "effect": "heartbeat", "brightness": 60 } },
    { "id": "beep", "kind": "sound",
      "settings": ["volume", "melody"],
      "melodies": ["short", "two_notes", "heartbeat"] },
    { "id": "btn", "kind": "button",
      "settings": ["press", "long_press"] }
  ]
}

The smallest one is a single light that only has a color:

{ "proto": 1, "parts": [ { "kind": "light", "settings": ["color"] } ] }

Fields

FieldType
protoint1. Needed
modelstringOptional, up to 32 characters. Shown on the owner’s card, never anywhere else
firmwarestringOptional, up to 32 characters. Shown on the card
wantsstring[]receive and/or send. Read only once, at setup over Bluetooth, and becomes the device’s requested_capabilities: the most it can ever be allowed. Later abouts never widen it; only setting up again does
partsobject[]Needed, at most 8
parts[].idstring[a-z0-9_]{1,16}, unique in the device. Defaults to kind, so two parts of one kind need ids of their own
parts[].kindstringOne of the catalog
parts[].settingsstring[]The settings this part really has, from its kind’s list. List only what you have: the apps show only these
parts[].effects, parts[].melodiesstring[]The device’s own list for effect and melody, 16 names at most. Names from the catalog get a translated label in the apps; any other name [a-z0-9_]{1,24} passes and is shown as it is; a name that doesn’t fit is dropped. Without its list, effect or melody is no setting
parts[].ledsintA light’s LED count, for the card. Optional
parts[].defaultobjectThis part’s defaults where they differ from the platform’s. A default that fails the checks is dropped; a button’s can’t name a contact
  • The whole about is at most 4 KB as sent.
  • Unknown kinds, settings and fields are dropped, so a newer firmware works with an older server. The server keeps the raw about and reads it through the catalog each time, so they appear once it learns them. The device object’s about is that reading: every id filled in, known settings only, on listed where the kind has it.
  • Send it at every boot. An about that drops a part, a setting or an effect drops the owner’s value for it too, and rev changes.
  • On Bluetooth it travels with "type": "about", like every message there.

Each setting ends with the platform’s default. Numbers are whole.

  • A part’s default wins over the platform’s.
  • Battery is a report, not a setting: battery 0–100 comes with state and shows in the card’s header.
  • Two parts of one kind are fine: the row title in the app then carries the part’s id.

Settings

The settings message

One object carries a device’s settings everywhere: in REST responses, on the stream and over Bluetooth.

{
  "type": "settings",
  "rev": "r3f9a0c1d2e",
  "name": "Ring in the hall",
  "capabilities": ["receive", "send"],
  "tz": "Europe/Lisbon",
  "utc_offset": 0,
  "now": "2026-11-28T10:00:00Z",
  "values": {
    "ring": { "on": true, "color": "#E86A9A", "brightness": 60, "effect": "heartbeat",
              "speed": 50, "duration": 3, "idle": "off" },
    "beep": { "on": false, "volume": 40, "melody": "short" },
    "btn":  { "press": { "anyone": true }, "long_press": { "contact": "DXEjjB91rJYQvgaGGdsx" } }
  }
}
FieldType
revstringThe revision. Opaque: apply it, echo it back, never compare two. It is a hash of what the device applies (name, capabilities, tz, values), so it changes with any of them, and only then
namestringThe name the owner gave the device, for a screen
capabilitiesstring[]What it may do now: receive, send, or neither. A toy honors it itself: without receive it shows no hearts, without send its button sends nothing
tzstringThe device’s time zone, like Europe/Lisbon; without one, its quiet hours’ zone, else UTC
utc_offsetintThe offset from UTC in minutes now: an ESP32 or a toy can’t read an IANA zone
nowstringThe time when this was sent, for a device without a clock
valuesobjectBy part id, then by setting. Always complete: the server fills in the defaults

It comes only to a device that has sent its about: as the answer to PUT about, on the stream right after ready and after every change (values, name, capabilities, time zone, a button’s contact deleted), and in GET /v1/devices/self. Always the whole thing. Apply it, keep it across reboots, then report the rev you applied (below). Skip a setting or a part you don’t know.

Button targets

A button’s target is written the way a signal writes to, so the firmware pastes it straight into POST /v1/events:

ValueThe press
{ "contact": "DXEjjB91rJYQvgaGGdsx" }Sends a heart to this person. Only for a device with send, and only someone in its book (else 400 no_send or bad_value)
{ "anyone": true }Sends a heart to someone out there
nullDoes nothing. The default
 
{ "type": "signal", "to": { "contact": "DXEjjB91rJYQvgaGGdsx" } }

When the owner deletes that contact, the target becomes null (not the default), rev changes and the device gets its settings again. A device without send gets null for every target.

Applying: rev and state

The server keeps the values the owner wants with their rev, and the last rev the device reported as applied. While the two differ, the app says the change will apply once the device is online. Report it with POST /v1/devices/self/state over Wi‑Fi, or with an applied message over Bluetooth. A new token makes the server forget what was applied: the device starts over.

preview

{ "type": "preview" }

The owner tapped Try it on the card: show one heart, exactly as the device is set now. It is not a signal: it only ever goes from the owner to their own device, at most once a second. It reaches a device that is online right now, or nobody. The app gets 409 offline when the device has no open stream, no_about before it sent an about, phone_link for a Bluetooth-only toy (the phone shows it itself), and 429 too_many more often than once a second.

Over Wi‑Fi

With its device token, a Wi‑Fi device uses these routes on https://api.lovearound.me, besides POST /v1/events for sending.

GET/v1/devices/selfdevice

The device as its card shows it, plus tz, utc_offset and now, and once it has sent an about, rev and values: the fields of the settings. For a device that can’t keep a stream open. An app’s sign-in gets 403.

PUT/v1/devices/self/aboutdevice

The about, at every boot. The response is 200 with the settings, already checked against this about: a device that sleeps between hearts needs only this one call. Errors: 413 too_large, 400 bad_json, bad_about, too_many_parts, bad_part_id, duplicate_part.

POST/v1/devices/self/statedevice
{ "rev": "r3f9a0c1d2e", "battery": 80 }

Either field or both; the response is 204. Send rev exactly as the settings gave it, after applying them, and battery (0–100) when it has changed noticeably, on its own too. The owner’s apps then get {"type":"sync","what":"devices"}. Errors: 400 bad_value for a malformed rev or battery, 400 bad_request for an empty body. Never send state because a heart was shown: see privacy.

PATCH/v1/devices/selfdevice

A change like PATCH /v1/devices/{id}, within what the device asked for when it was set up; it may also set its own tz (an IANA name, else 400 bad_tz; null for none). book is refused with 403 not_allowed: a device can’t widen whom it sees.

GET/v1/contactsdevice, send permission

As before, with two changes for a device: each contact also has rgb, its color as #RRGGBB, so firmware needs no table of the 12; and the list has only the people the device’s book allows: everyone, close people, or the ones the owner picked. A device set up over Bluetooth starts with close people. Older devices see everyone. The book only filters this list: POST /v1/events doesn’t check it. When the book changes, a device that may send gets {"type":"sync","what":"contacts"}.

On the stream

  • After ready, and after every change, comes {"type":"settings", …}: always the whole thing. Only for a device that has sent its about.
  • {"type":"preview"} when the owner taps Try it.
  • {"type":"sync","what":"contacts"} as before, but only to apps and to devices with send.
  • The stream also opens for a device without receive, with no 403: it gets settings and sync, no signals, and it is never picked for a signal to anyone.
  • A change of rights or a new token still closes the stream. A change of values doesn’t: a new settings comes instead.
  • The stream stays one-way. Report applied and battery over REST.

What the apps call

For reference: the owner’s apps do this with the person’s sign-in, never with a device token. Changing settings looks like this:

PATCH /v1/devices/{id}/settings
{ "values": { "ring": { "brightness": 80 }, "beep": { "volume": null } } }
Request
PATCH /v1/devices/{id}/settingsThe example above: merged into the stored values, null means back to the default. Checked against the device’s about: the kind, the setting, the range, the device’s own lists. The answer is the device; the settings goes to its stream. Errors: 409 no_about; 400 unknown_part, unknown_setting, bad_value, no_send, with part and setting; 429 too_many past 10 a minute per device: the apps hold sliders back
POST /v1/devices/{id}/previewTry it: 202; 409 offline, no_about, phone_link; 429 too_many
PATCH /v1/devices/{id}As before, plus tz (else 400 bad_tz) and book: "all", "close" or a list of contact ids (else 400 bad_book)
POST /v1/devicesAlso takes setup ("bluetooth", else 400 bad_setup), link ("server" or "phone", else 400 bad_link) and tz. With link: "phone" there is no token: 201 {device}
POST /v1/devices/{id}/tokenAlso for a device set up over Bluetooth: setting it up again. 409 for a device paired by code, 409 phone_link for a Bluetooth-only toy
PUT /v1/devices/{id}/about, POST /v1/devices/{id}/stateThe phone, for a Bluetooth-only toy only: 409 server_link for any other device

The device object gains setup (app, code or bluetooth), link (server or phone), tz, book, online (a stream of it is open now; missing for a Bluetooth-only toy) and about; once there is an about, rev and values (complete); and applied and battery once the device has said them. The owner’s apps get {"type":"sync","what":"devices"} when a device’s about, applied rev, battery or values change.

Setup over Bluetooth

A board with Bluetooth gets its Wi‑Fi and its token from the phone: no token in the firmware, no access point. It uses Espressif’s Wi‑Fi provisioning: WiFiProv in Arduino, wifi_provisioning in ESP‑IDF, the ESPProvision libraries on iPhone and Android. Security 2 (SRP6a and AES‑GCM), which builds on arduino‑esp32 3.3 and 4.0 alike. Until device codes come, every board uses the same public credentials: username lovearound, password lovearound. Listening in still gives nothing; a look-alike device is not stopped yet. Later a code from the board’s screen or sticker replaces the password, with the same mechanism; the apps can already enter one.

An example firmware is coming; there is no code here yet.

The order

  1. Setup mode. A new board, or one after a long press, is in setup mode for 5 minutes and advertises as LoveAround-XXXX. Espressif’s proto-ver reports security version 2. The app lists only boards very near.
  2. about and the confirm screen. The app reads about from the custom endpoint lovearound-about and shows what the device wants (receive, send) before anything is made.
  3. Wi‑Fi first. The app sends the Wi‑Fi name and password, and the board reports that it’s connected; keep provisioning running after that (disableAutoStop). Only then does the app create the device, POST /v1/devices { "name", "setup": "bluetooth", "capabilities", "tz" } → 201 {device, token}, and send the token through the custom endpoint lovearound-token. A wrong password leaves nothing on the account. The device counts as paired: its wants become requested_capabilities, and it can only be narrowed from there. Its book starts as close.
  4. Bluetooth off, then the server. Free Bluetooth before the board’s first TLS connection. The app waits for that first connection and deletes the device if it never comes.
  5. From then on the board works as in Over Wi‑Fi.
  • Out of setup mode the board takes nothing over Bluetooth.
  • In setup mode a working board keeps working and never gives out its token or its Wi‑Fi.
  • A 401 from the server wipes the token and the values: the device was disconnected.
  • A board without Bluetooth (ESP32‑S2) uses pairing by code instead.

Setting up again

A new Wi‑Fi password, a new place: the owner puts the board into setup mode and the app runs the same steps, but asks for a new token for the same device with POST /v1/devices/{id}/token. The device keeps its name, values and quiet hours. The old token stops at once, and the server forgets what the device applied: it reports its rev again after the first settings.

Notes for firmware

  • Arduino’s WiFiProv has no custom endpoints. Call network_prov_mgr_endpoint_create() and network_prov_mgr_endpoint_register() between initProvision() and beginProvision(). We haven’t tried this yet.
  • A 4 MB board needs a partition table with room for Wi‑Fi, Bluetooth and TLS together. Pick it before updates over the air arrive, since it can’t change after.

Bluetooth-only toys

A toy without Wi‑Fi talks to the owner’s phone, and the phone talks to the server. One toy, one phone: a toy bonds with one phone. A new bond is possible only in setup mode (a long press, 5 minutes) and replaces the old one.

The GATT service

One service for every lovearound toy, 80e80001-eb5b-4050-86c3-f6516f771280, with two characteristics:

CharacteristicUUID
rx80e80002-eb5b-4050-86c3-f6516f771280Phone → toy. Write with response
tx80e80003-eb5b-4050-86c3-f6516f771280Toy → phone. Indicate

Both carry the same typed JSON as everywhere else:

MessageWay
abouttoy → phoneThe about, with "type": "about"
settingsphone → toyThe settings, when the phone is near and they changed
appliedtoy → phone{ "type": "applied", "rev": "r3f9a0c1d2e" }
eventphone → toyA signal: the same object as on the stream
previewphone → toyTry it
presstoy → phone{ "type": "press", "part": "btn", "gesture": "press" }; gesture is press, long_press or double_press
forgetphone → toyErase the bond and the values, see below

Battery goes through the standard Battery Service (0x180F), not this one.

Framing

  • A message longer than one packet goes in chunks. Each chunk starts with one flag byte: 0x01 when more follows, 0x00 on the last one. The rest of the chunk is the next bytes of the JSON.
  • A message is at most 4 KB.
  • Drop a half-received message when the link drops.

Bonding and forget

  • Every characteristic needs an encrypted, bonded link. A phone that isn’t the bonded one gets nothing.
  • forget and a factory reset erase the bond and the values, and on a board with Wi‑Fi also the token and the Wi‑Fi.
  • iOS can’t unpair from an app. So Disconnect in the app sends forget when the toy is near, and says how to reset it when it isn’t.

How hearts arrive

  • iPhone: iOS hands notifications to a bonded accessory by itself, through ANCS, even with our app asleep. The toy shows a heart for a lovearound notification, following the ANCS rules. This works while lovearound notifications are allowed on the phone and the phone is near; the phone’s quiet hours and its “someone out there” setting apply.
  • iPhone, app open: then the app shows no banner, so iOS forwards nothing, and the open app writes event itself.
  • Android: the server’s push wakes our app, and it writes event.
  • Merge: a trigger that comes while a heart is showing joins it. This also covers one heart that arrives both ways.
  • The button: a press wakes our app over Bluetooth, and the app sends as the button’s settings say. On iPhone, not after the app was swiped away.

ANCS rules

iOS hands a bonded accessory the notifications of every app. Every firmware must keep to these rules:

  1. Ask only for the app identifier. For a new notification, ask for its App Identifier attribute and nothing else. Never ask for the title, subtitle or message of another app’s notification.
  2. Only me.lovearound.ios. Ignore every other app.
  3. No subtitle is a heart. A heart notification never has a subtitle. Any other notification the app may add will have one: ignore it. Ask for the subtitle only of a me.lovearound.ios notification.
  4. No replays. Skip notifications flagged PreExisting and the events Modified and Removed: act only on a fresh Added. Otherwise every reconnect would show old hearts again.

What iOS still does: a Focus doesn’t stop the forwarding, and a Scheduled Summary forwards late. Apple’s Accessory Notifications, where the person picks which apps an accessory gets (in the EU, iOS 26.4 and later), comes later.

On the server

  • The phone registers the toy with POST /v1/devices { "name", "setup": "bluetooth", "link": "phone", "capabilities" } → 201 {device}, with no token. It posts the toy’s about and state for it with PUT /v1/devices/{id}/about and POST /v1/devices/{id}/state, and the values live on the server, so the toy’s card is the same as any device’s.
  • The server can’t deliver to the toy itself: the toy shows what the phone gets. So its card hides who can reach it, accept_anyone and quiet_hours are refused with 400 phone_link (quiet_hours: null passes), preview answers 409 phone_link (the phone writes it to the toy itself), and its online is missing.
  • capabilities travel inside settings, so switching off Receives hearts reaches the toy too.

Compatibility

  • Skip what you don’t know: message types, fields, parts and settings in values. The server and the apps do the same with yours: unknown parts and settings are dropped, unknown kinds aren’t shown.
  • Names outside the catalog in effects and melodies pass, and the apps show them as they are.
  • rev is opaque; never compare it or parse it.
  • about never widens what a device may do; only setting up again does.
  • Later, not in v1: custom settings with their own labels, a device narrowing a range (say, brightness at most 60), a device changing its own values (a knob), a code at setup, updates over the air, two accounts sharing one toy.

Errors and limits

Every error, on these routes and all the others, is JSON with a code for programs, and part and setting when it is about one:

{ "error": "brightness: 1-100", "code": "bad_value", "part": "ring", "setting": "brightness" }

error is for people and may change; code stays. Decide by the HTTP status and code.

Privacy rules for makers

With only a handful of people on lovearound, small details give a sender away. Every firmware keeps to these:

  • No model name in X-Client or User-Agent. Leave X-Client out, or use a generic name. For a device token the signal log says device and nothing more, never a model or a firmware: with this few people, a model name is the sender. model and firmware in about go only to the owner’s card.
  • Never report a heart you showed. No acknowledgement, no counter, no state sent because of a heart, no log of when hearts came.
  • Only our notifications. Over ANCS, read nothing of other apps’ notifications but their app identifier.
  • No sender, ever. Don’t try to tell hearts apart by who sent them: nothing in a signal says it, and the platform will never add it.
