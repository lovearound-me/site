REST API

Anything that changes state or sends a signal is a plain HTTP request with JSON.

Basics

https://api.lovearound.me
  • Authorization: Authorization: Bearer <token> on every request. The kinds of token are in the overview.
  • Request body: JSON with the Content-Type: application/json header.
  • Time: ISO 8601 strings in UTC, for example 2026-10-10T14:00:00.000Z.
  • X-Client (optional): the client’s name and version, for example my-lamp/1.2, up to 64 characters. It goes into the server log along with the signal and helps track down problems. Without it, the log gets the User-Agent.
  • From a web page: the server answers CORS only for https://app.lovearound.me and for http://localhost or http://127.0.0.1 on any port, so a page of your own can be tried locally. Never *.

Each request is marked with who may call it:

app — a signed-in person’s token only; a device gets 403. device — a device token works too. no token — nothing in Authorization.

Errors

An error comes with an HTTP status and a body:

{ "error": "already in contacts" }

The text in error is for people and logs. Decide by the status code, not the text.

CodeWhen
400The request makes sense but a value is wrong: an empty label, a malformed code, a color outside 0–11, nothing to change. Also 400 when the body isn’t valid JSON
401No token, or it’s wrong or expired; the device was disconnected or its account deleted
403A device token can’t do this: the request is app-only, or the device lacks the permission
404No such contact or device in your account, or no such pairing code
409The person is already in the list, there are already 12 close people, or there are already 20 devices
410Pairing by code: the code ran out or its token was already taken. Ask for a new code
415No Content-Type: application/json
422The JSON doesn’t fit the schema: a required field is missing, an extra field in an event, a wrong type. The response body here is plain text, not JSON
429A limit was hit, see below
503The server is updating, or a part of it didn’t answer. Retry in a couple of seconds
5xxSomething failed on the server. Retry later, with a pause

Signals

POST/v1/eventsdevice, send permission

Send a signal to a person in your list:

{ "type": "signal", "to": { "contact": "DXEjjB91rJYQvgaGGdsx" } }

Or to a random person online who accepts signals from anyone (never to yourself):

{ "type": "signal", "to": { "anyone": true } }
FieldType
typestringOnly "signal" for now. Anything else is 400
to.contactstringA contact’s id from GET /v1/contacts
to.anyonebooltrue — someone out there. Not allowed together with contact

A signal has no data field: with one, you get 400. There must be no other fields either, or you get 422.

The response is 202 Accepted:

{ "id": "ev_q8ZkT1mW4aLp0sXv7cRb" }

202 means “accepted”. The response doesn’t say whether the recipient was online or how many devices they have. A signal to a contact added with a wrong Love ID, or with one that has stopped working, is accepted too and goes nowhere. “Anyone” also returns 202, even when nobody is online.

Besides the recipient’s open streams, a signal to a contact also shows up in their chat with the Telegram bot, if they have one. A signal to anyone goes to one person: among open streams with anyone=true and Telegram chats that take such signals. One person gets at most one of those an hour.

Errors: 400 a wrong type or to, 403 the device may not send, 404 no such contact, 429 “anyone” was already used this hour (every attempt counts).

Contacts

The contact object:

{
  "id": "DXEjjB91rJYQvgaGGdsx",
  "label": "Mom",
  "position": 0,
  "close": true,
  "color": 3,
  "created_at": "2026-10-02T09:12:44.120Z",
  "invite_url": "https://lovearound.me/i/GSSV7-A33HN"
}
FieldType
idstringThe person’s identifier in your list. Other lists know nothing about it
labelstringYour label, 1–64 characters. The person never sees it
positionintOrder in the list
closeboolA close one: a circle at the top of the apps and on the Telegram bot’s home. Handy to show first. 12 at most
colorintYour color for them, 0–11, see colors. Like the label, only you see it. Missing on an old entry that has never been given one
created_atstringWhen they were added
invite_urlstringThe link they were added by, to pass them on. Only with an app token, never with a device token; missing on old entries

A contact is tied to the Love ID it was added by. If that Love ID stops working (the account was deleted or merged into another), signals to the entry are still accepted and go nowhere. invite_url is always the link you added them by, not the person’s current one, and it comes back the same whether anyone is behind it or not.

GET/v1/contactsdevice, send permission

The whole list, by position, then by when they were added.

{ "contacts": [ { "id": "DXEjjB91rJYQvgaGGdsx", "label": "Mom", … }, … ] }

When the list changes, a sync arrives over WebSocket: load it again then.

A device without the send permission gets 403 here: it has nobody to send to, so it doesn’t see your people.

POST/v1/contactsapp

Add a person by their Love ID:

{ "code": "GSSV7-A33HN", "label": "Mom", "close": true, "color": 3 }

code is 10 characters from 23456789ABCDEFGHJKMNPQRSTVWXYZ; case and dashes don’t matter. close is optional and defaults to false. color is optional: without it the contact gets, at random, a color nobody in your list has yet. A new contact goes to the end of the list.

The response is 201 with the contact object. A wrong but well-formed code also gets 201: the server doesn’t say whether anyone is behind a code. With 12 close people already, the new one is added as not close and the response says "close": false.

“Already in the list” means the same code. The same person added by another link of theirs becomes a second entry: the server never tells whether two links lead to one person.

Errors: 400 a malformed code, an empty label or one longer than 64 characters, a color outside 0–11, your own code, 200 people already in the list. 409 this code is already in the list. 429 too many additions this hour.

PATCH/v1/contacts/{id}app

Change the label, the position, the “close” mark or the color. Any subset of the fields:

{ "label": "Mommy", "position": 2, "close": false, "color": 7 }

The response is 200 with the updated contact. To reorder several people, send one request for each. Errors: 400 an empty body, a bad label or color, 404 no such contact, 409 marking a 13th close person.

DELETE/v1/contacts/{id}app

Remove from the list. The response is 204, also when the contact is already gone. The person isn’t told.

Devices

The device object:

{
  "id": "r7Hc2LqW9xPz4KmN0aTe",
  "kind": "toy",
  "name": "Kitty on the shelf",
  "capabilities": ["receive", "send"],
  "created_at": "2026-10-20T18:03:10.442Z",
  "last_seen_at": "2026-11-01T07:55:02.918Z"
}
FieldType
kindstringtoy or custom; a device paired by code can also be watch or lamp. Skip values you don’t know
namestring1–64 characters
capabilitiesstring[]receive — receive signals, send — send them and read the contact list
last_seen_atstringWhen the device last opened a stream. Missing if it never has
GET/v1/devicesapp

The devices, by creation time: { "devices": [ … ] }.

POST/v1/devicesapp
{ "name": "Kitty on the shelf", "kind": "toy", "capabilities": ["receive"] }

kind defaults to custom, capabilities to both. The response is 201:

{ "device": { "id": "r7Hc2LqW9xPz4KmN0aTe", … }, "token": "dev_4kq9XbT2mWc7RfLp8sHn3vYzAe6uJd5G" }

The token is shown only here; the server keeps just its hash. Errors: 400 a bad name, kind or capabilities, 409 there are already 20 devices.

DELETE/v1/devices/{id}app

Disconnect a device. Its token stops working at once and the streams it opened are closed. The response is 204, or 404 if there is no such device.

Pairing a device by code

For a device with a screen and no way to sign in, like a watch or a lamp with a display. Instead of a token pasted into its firmware, it shows a code, and the person confirms it while signed in. The device then gets a device token of its own, as if it had been made in Settings → Devices.

  1. The device asks for a code with POST /v1/pairing, saying what it is and what it needs. It gets six digits, a secret and a link.
  2. It shows the digits and a QR code of the link, and keeps the secret to itself.
  3. The person opens the link, or types the digits at lovearound.me/login/devices, signs in if needed and sees a card: the device’s name and what it will be able to do. They tap Connect: the web app calls find and then confirm.
  4. All this time the device asks POST /v1/pairing/token with its secret. Once the code is confirmed, it gets its token, once.

The digits alone never give the token: it goes only to whoever holds the secret, so someone who sees the screen can’t take it. The server takes codes and secrets only in request bodies, so they never land in a request log; the link keeps the code after #, which a browser doesn’t send anywhere.

A paired device works like any other: it receives signals with receive and sends them with send. Like any device, it reads the contact list only if it may send: one that only receives gets 403 from GET /v1/contacts, and its card says it won’t see your people. It’s listed in GET /v1/devices and disconnected like any device.

POST/v1/pairingno token

The device asks for a code:

{ "name": "Apple Watch", "kind": "watch", "capabilities": ["receive", "send"] }
FieldType
namestring1–64 characters, shown on the card and in the device list
kindstringwatch, lamp, toy or custom. Optional, custom by default
capabilitiesstring[]receive and/or send. Optional, both by default

The response is 201:

{
  "code": "482913",
  "secret": "Hq3ZbT8mWc7RfLp2sKn9vYzAe6uJd5Gx",
  "url": "https://lovearound.me/login/devices#482913",
  "expires_in": 600,
  "poll_every": 3
}

Show code and a QR code of url. The code is good for expires_in seconds, once; after that, ask for a new one. Ask for the token every poll_every seconds. Errors: 400 a bad name, kind or capabilities, 429 too many codes from this IP this hour, 503 too many codes open right now: try again a bit later.

POST/v1/pairing/findapp

The card for a code: what the device is and what it asked for.

{ "code": "482 913" }

Spaces and dashes between the digits are fine. The response is 200:

{ "name": "Apple Watch", "kind": "watch", "capabilities": ["receive", "send"], "expires_in": 512 }

expires_in is how many seconds the code has left. Errors: 404 no such code (wrong, run out or already confirmed: they all look the same), 429 too many wrong codes this hour.

POST/v1/pairing/confirmapp

“Connect”: the device joins your account with what its card showed.

{ "code": "482913" }

The response is 201 with the new device:

{ "device": { "id": "Lw4Np8RkT2cYq9ZaH3mV", "kind": "watch", "name": "Apple Watch", … } }

Its token now waits two minutes for the device to ask. A device that never asks stays in the list as never connected; disconnect it there. Errors: 404 and 429 as for find, 409 there are already 20 devices.

POST/v1/pairing/tokenno token

The device asks whether its code was confirmed:

{ "secret": "Hq3ZbT8mWc7RfLp2sKn9vYzAe6uJd5Gx" }
CodeWhat to do
202{ "status": "waiting" }: not yet. Ask again in poll_every seconds
200Confirmed. Keep the token: it’s given only this once
410The code ran out, the token was already taken, or the secret is wrong. Start over with POST /v1/pairing
 
{
  "token": "dev_8sHn3vYzAe6uJd5G4kq9XbT2mWc7RfLp",
  "device": { "id": "Lw4Np8RkT2cYq9ZaH3mV", "kind": "watch", … },
  "account": "anna@example.com"
}

account is the email of the account the device joined, to show on its screen; null if that sign-in has none. From here on the device uses the token like any other: Authorization: Bearer dev_….

Codes live in the server’s memory: after an update it answers 410, and the device asks for a new code.

Account

GET/v1/meapp

Your own account. On the first call after sign-in, the server creates it and issues a Love ID.

{
  "uid": "…",
  "created_at": "2026-09-28T11:40:00.000Z",
  "invite_url": "https://lovearound.me/i/GSSV7-A33HN"
}

uid is your own identifier. The server never hands out anyone else’s.

DELETE/v1/meapp

Delete the account with all its data: the list, devices and their tokens, the Love ID, the sign-in, the chat with the Telegram bot. Open streams are closed. The response is 204. This can’t be undone.

POST/v1/me/mergeapp

Fold another account of yours into the one you’re signed in to. The web app does this in Settings → Account → Sign-in methods when a way in you’re adding turns out to belong to another account. Both sign-ins are needed: your usual token in Authorization, and in the body an ID token of the other account from a sign-in at most 10 minutes ago.

{ "token": "<the other account’s ID token>", "confirm": false }

Without confirm, nothing changes: the response says what would happen.

{
  "here": 14,
  "contacts": 6,
  "devices": 1,
  "added": 4,
  "invite_url": "https://lovearound.me/i/8HXNW-3DCVF",
  "telegram_here": true,
  "telegram_there": false,
  "ways": ["apple.com", "google.com", "password"]
}
Field
herePeople in this account’s list
contacts, devicesPeople and devices in the other account
addedHow many of those people would join this list
invite_urlThe other account’s Love ID, which will stop working; null if it has none
telegram_here, telegram_thereWhether each account has a chat with the Telegram bot
waysThe ways to sign in this account will have afterwards

With "confirm": true it’s done, and the response is { "contacts": 4, "devices": 1, "linked": true }:

  • People join at the end of the list with their ids, labels and colors. Skipped: anyone already here by the same code, and entries for either account itself. They stay close while there’s room for 12, and the list stops at 200.
  • Devices move with their ids and tokens; their streams reconnect to this account.
  • The other account goes like a deleted one: its Love ID stops working, its streams are closed and its apps ask to sign in again. Its Telegram chat moves here if this account has none.
  • Its Google and Apple sign-ins move here, unless this account already has one of that kind. A password doesn’t move. "linked": false means a sign-in didn’t move; it’s free by then and can be added again.
  • Nobody else learns anything: other people’s lists stay as they were.

Errors: 400 it’s the same account, 403 the other token isn’t valid or its sign-in is older than 10 minutes: sign in to it again. It’s 403, not 401, so that an app doesn’t sign you out of this account.

POST/v1/telegram/linkapp

A one-time link that joins a chat with the Telegram bot to this account; the page lovearound.me/signin?telegram=1 calls it. No body. The response is 200:

{ "url": "https://t.me/LoveAroundMeBot?start=link_…" }

The link is good for 10 minutes, once; whichever Telegram opens it joins the account. From a browser, only lovearound.me may call this. Errors: 503 the bot didn’t answer: try again.

Stream

WS/v1/streamdevice, receive permission

Receiving signals. Described in WebSocket.

POST/v1/stream/ticketapp

A one-time ticket for opening the stream from a browser, which can’t put the token in a header there. No body.

{
  "ticket": "k3VqT9…",
  "expires_in": 30
}

Open /v1/stream?ticket=… within expires_in seconds. A ticket works once and only for the stream.

Health check

GET/no token

Answers 200 with the text needed.

Try it from a terminal

TOKEN=dev_…
API=https://api.lovearound.me

curl -H "Authorization: Bearer $TOKEN" $API/v1/contacts

curl -X POST $API/v1/events \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"type":"signal","to":{"contact":"DXEjjB91rJYQvgaGGdsx"}}'

Pairing by code, playing the device:

curl -X POST $API/v1/pairing \
  -H "Content-Type: application/json" \
  -d '{"name":"Desk lamp","kind":"lamp","capabilities":["receive"]}'

# confirm the code at lovearound.me/login/devices, then:
curl -X POST $API/v1/pairing/token \
  -H "Content-Type: application/json" \
  -d '{"secret":"…"}'
